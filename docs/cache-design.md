# 缓存后端与性能研究

状态：研究草案，尚未实现 SQLite 后端或改变缓存一致性。整理基线为本地提交 `4889726`。本文区分官方资料、现有代码观察、本机测量和后续设计建议。

## 初步决策

保留 `files` 与 `sqlite` 两种可选后端；已有配置继续默认文件后端，SQLite 先作为显式选项。优先把缓存放在运行机器的本地盘，即使原文位于网络挂载上。文件/SQLite 后端选择和缓存位置是两项独立设置，不能从“文档在 FUSE 上”推导“缓存也必须在 FUSE 上”。

用户提到的“fuse9”尚未确定具体实现；本研究按 FUSE/9p 一类挂载讨论。FUSE 是用户态文件系统机制，9p 是文件共享协议，两者不等同于某一种网络存储，也不能仅凭名称判断锁、同步、随机读和元数据性能。实际部署需要记录具体驱动、服务端、挂载参数及使用主机数。

## 现有耗时路径

- `pkg/doclibrary/library.go:330`：每次 search/index 都从根遍历目录，处理 include/exclude、文件信息与配额。
- `pkg/doclibrary/cache.go:26`：每个文件先读取原始字节、计算 SHA，再确定缓存键；命中后仍打开 JSON 文件并完整反序列化。PDF 暖命中省去的是 Poppler 提取，不是原文 I/O。
- `pkg/doclibrary/engine.go:400`：搜索逐文档遍历，源码重新分段、归一化、匹配，再合并与排序；目前没有倒排索引。
- `pkg/doclibrary/frequency.go:46`：主动查询使用文件锁，读取并更新整个频次集合，排序、截断后写临时文件、同步并原子替换。默认最多256条，是否值得改成行级更新需实测。
- `frequent` 即使 passive 也会按源文档重新读字节计算 SHA；passive 只免去频次更新。

因此，单纯把 JSON 文件原样放进 SQLite BLOB，只能改变存储 I/O 与事务管理，不能自动省去源文件 SHA、JSON 解析、分段和全库搜索。性能优化应按阶段测量，不能把几个操作耗时相减直接当作准确的 CPU/I/O 分解。

## 本机基线测量

本轮使用基线CLI，资料为YanTrace、exam-zh与LuaDraw共231文件、13,204,743字节（约12.59MiB）；源与缓存均位于同一ext4挂载。每个case先同配置预热1次，再独立启动CLI测5次，时间含进程启动、执行与响应JSON解析；不清操作系统页缓存。频次开/关使用各自namespace，各自预热，避免把配置切换后的首次提取算成暖命中。search请求为 `query="函数 定义", match="any", limit=8`。

| status | 开 | 82.1 | 80.7—145.6 | 0/0（只扫描） |

| search | 开 | 349.8 | 334.6—398.8 | 231/0 |
| frequent passive | 开 | 10.4 | 9.9—11.3 | 不统计提取缓存 |

本地证据：`build/cache-research/benchmark.py`、`results.json`、两份开发期配置副本；复现：`/home/lingnc/miniconda3/bin/python build/cache-research/benchmark.py`（Conda base已有PyYAML）。报告包含CLI/config哈希、源文件清单与大小、挂载信息、每次样本和缓存计数。未实测SQLite后端或网络挂载，不能从这些数据宣称SQLite快多少。现阶段可以确认：全命中后仍有目录扫描、原文SHA、提取结果解码与搜索工作，替换缓存容器并不能自动消除它们。

## SQLite 与文件的适用范围

| 场景 | 建议 | 理由与限制 |
| --- | --- | --- |
| 本地盘，少量文件、偶发读取 | 两者均可，保留files默认 | 直接文件简单；SQLite连接与SQL开销未必值得 |
| 本地盘，大量小片段、频繁更新频次 | 优先试验SQLite | 减少逐对象打开/关闭；短事务批量更新，便于版本管理与GC |
| 原文在FUSE/NFS，缓存能放本地盘 | 优先本地缓存，后端再测 | 先避免缓存也承担网络元数据与随机I/O；原文严格SHA成本仍在 |
| 缓存只能放远端挂载 | 不直接套用SQLite WAL | 需确认锁/同步/重命名与随机读性能；文件后端也依赖这些语义 |
| 多台主机共享可写缓存 | 优先每台机器独立本地缓存 | SQLite WAL不适用跨主机网络文件系统；现有文件锁也未验证跨主机行为 |

SQLite 官方的“小对象比独立文件快约35%”研究使用约10KB BLOB、特定设备和暖缓存，且正文明确承认不同系统与冷缓存可能相反。这支持把SQLite列为候选，不支持预先承诺本项目提速比例。

SQLite WAL 支持读写并行，但同一时刻仍只有一个写者，并额外使用 WAL/SHM 文件。官方明确不适合跨主机网络文件系统。改成回滚日志可绕开WAL共享内存限制，但不会修复挂载本身不可靠的锁与fsync，也不保证比文件快。

文件后端当前使用flock/LockFileEx、临时文件同步与rename；若底层挂载不支持相应语义，它同样不能自动成为可靠的共享缓存。不要为追求基准数值禁用锁或同步。

## 双后端设计建议

第一阶段仅抽象存储层，共享现有授权、提取、SHA失效和匹配逻辑，保持JSON/JSONL响应与定位语义。配置新增后端选择时沿用现有 `cache_dir` / `cache_mode`，未配置后端时保持files；不要根据挂载类型静默切换后端。新增字段目前尚不存在，不能直接填入当前严格配置。

存储接口应覆盖提取结果get/put、文档修订信息、频次原子更新/列举、失效/清理与close。提供批量读取和事务更新能力，避免把逐文件调用机械替换成逐行短连接查询。Go API连接生命周期需明确；schema/status不得因后端初始化而扫描PDF。

SQLite 可将集合身份、文档修订、PDF页/段落和频次分表；内容身份保留 source/doc、SHA、提取器版本与算法版本，频次保留稳定entry_id和digest校验。授权检查仍在读取前执行。区分集合授权身份与纯运行参数，避免只改结果预算就创建整套重复提取缓存。按需读取PDF页/段落，而不是每次解码整本提取结果。

频次使用短事务UPSERT，提取与Poppler执行放在写事务之外；可接受初版并发重复提取后幂等写入，避免持锁执行耗时外部进程。连接池、busy_timeout、取消、checkpoint与GC策略要显式设计。初期以保守同步设置比较性能，不把削弱持久性得到的优势算成后端固有优势。

提取文本、页/段落、指纹、频次适合入库；原始资料仍留在原目录，Poppler快照和返回给调用方的PNG预览仍需受控本地临时文件。统一结构化缓存不等于完全消灭文件系统。

Go驱动优先评估无CGO的 `modernc.org/sqlite`，以延续原生Go构建和Windows交叉编译能力；正式选型时固定支持Go1.25的版本并检查依赖、许可证、包体积及真实性能。Python sqlite3微基准不能替代该驱动的生产验证。

## 一致性与搜索加速分别设计

后端与“多久重验原文”分开。第一阶段两后端都保持严格SHA，保留同size/mtime内容改写仍失效的既有保证。后续若增加stat快速模式或显式index快照模式，必须明确它们可能遗漏变化/短期陈旧，并作为用户选择；不能偷偷用mtime取代SHA。网络原文的优化应先研究此项和目录增量扫描。

SQLite FTS5属于进一步的搜索索引方案，不应与存储迁移绑在一起。当前搜索包含中英混排、中文短词、子串、phrase、正则和自定义权重；默认词元FTS不等价。trigram可用于子串候选召回，但FTS查询对少于3个Unicode字符的子串有局限；短词、正则与归一化必须有不会漏结果的回退，再用原匹配器复核。

同一进程/JSONL场景还应评估有上限的已解码结果与分段缓存，保持源内容校验后复用；两种持久化后端均可受益。

## 后续验收

比较files/SQLite时固定内容、返回结果、SHA策略与持久性保证。矩阵至少包括冷提取、暖search/read/index、同进程JSONL、多进程频次更新、原文变化与删除；区分本地ext4、实际FUSE/NFS挂载和“原文远端/缓存本地”。记录p50/p95、源字节与元数据操作、缓存读写字节、CPU/分配、锁等待、缓存体积与返回结果一致性。

正确性覆盖同size/mtime改写、来源过滤、路径边界、进程退出、数据库busy/损坏、迁移回退、passive不写、并发频次计数、GC不删除活跃版本以及Windows实跑。没有实际挂载测量时，不宣布任何网络文件系统后端更快。
